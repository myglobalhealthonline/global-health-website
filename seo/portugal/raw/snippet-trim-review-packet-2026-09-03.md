## What is being asked, and what is not

**What changes:** the meta description only — the ~155-character grey snippet under the
blue link in a Google result. Nothing on the page itself changes.

**What does not change:** the doctor's name, biography, qualifications, certifications,
credentials, OM registration number, specialty, languages, prices, durations, booking
behaviour, availability, or any visible page copy. The writer is scoped to a single
metadata field per record and verifies the rest is untouched inside the transaction.

**Why:** Google truncates meta descriptions at roughly 155–160 characters. These eleven
run **191–220**, so between a quarter and a third of each is cut mid-word and never
displayed. Every proposal is **a strict subset of the text already approved and live** —
words were removed, nothing was added, reworded, or invented. The OM registration number
and the opening booking clause are kept in every one.

**Clinical risk assessment:** the removed material is institutional and credential
detail (medical schools, hospital affiliations, society memberships, degrees). No
clinical claim, no scope-of-practice statement, no availability or outcome promise is
added or altered. Each proposal remains factually true because it asserts strictly less
than the currently approved text.

## On approval — the exact publication procedure

The hashes above are recomputed on every run of the reporter, so **regenerate them
immediately before publishing** rather than copying from this file:

```
node --import tsx backend/scripts/report-portugal-snippet-trim-drafts.ts
```

Approval is recorded by adding, for each of the eleven assets, a
`seo/portugal/clinical-review-register.csv` row carrying `publish_status: approved`,
`reviewer_name: Dr Tiago Miguel Figueira`, `reviewer_doctor_id:
cmp5r0if3002kssjug743x0p6`, `clinical_reviewer_professional_body: OM`, the review
timestamp, the official OM/ERS source references, and `approved_sha256` set to that
asset's hash above. **The register row is the approval** — it must be created from an
actual review, not derived from this document.

The proposed text must also replace the `optimized meta description` column of the
corresponding `seo/portugal/page-by-page-completion-matrix.csv` row, because the
gated writer parses its drafts from that matrix at runtime. Doing both keeps the
draft-versus-matrix equality that `seo/czechia/validate-artifacts.mjs` now enforces on
the Czech side (§38.2).

Then, per record:

```
node --env-file=.env --import tsx backend/scripts/patch-portugal-seo-metadata.ts --only=doctor:<slug>
```

for the dry run, and the same command with `--apply --source-sha256=<from dry run>
--approved-sha256=<hash> --reviewer-doctor-id=cmp5r0if3002kssjug743x0p6
--reviewed-at=<YYYY-MM-DD> --confirm=<token> --confirm-database=<identity>` to write.

## The seven tool-page fields are a separate problem

`assertPortugalSeoApplyAuthorized` rejects `targetKind === "tool"` outright — *"is
managed in a static runtime source"*. The eleven tool title and description proposals
in the CSV **cannot be published through this writer at any approval level**. They need
the Czechia frontend-overlay route, which does not exist for Portugal yet. Clinical
approval does not unblock them; a chosen publication mechanism does.
